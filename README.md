# Python Handbook

A small Flask app that turns plain `.py` files into a browsable, styled
cheat sheet — no CMS, no database, no hand-written HTML for content.
Every page you see in the browser is generated by parsing Python source
files that exist for their own sake as readable, runnable code.

## What this is

There are two independent kinds of content, each living in its own
numbered file series:

1. **Chapters** — general Python topics (basics, control flow,
   functions, files, OOP, third-party packages, fetching data...).
   Read top to bottom like a course.
2. **Interview questions** — one file per LeetCode-style category
   (arrays & hashing, two pointers, sliding window, trees, graphs,
   dynamic programming, etc.), each holding zero or more worked
   exercises with a problem statement, an optional hint, a collapsible
   solution, and an explanation.

The `.py` files are the source of truth. A small "loader" module reads
each file, parses a comment-based mini-format out of it, and hands
structured data to Flask, which renders it through the `markdown`
library. **You never write HTML to add content** — you write (or edit)
a `.py` file.

## Project layout

```
app.py                     Flask routes + Markdown rendering
content_loader.py          Parses units/*.py -> load_units()
interview_loader.py        Parses interview_questions/*.py -> load_categories()
units/                     One file per chapter (01_basics.py ... 08_fetching_data.py)
interview_questions/       One file per interview-question category (18 total)
templates/                 base.html (sidebar shell) + index/unit/category pages
static/                    style.css (hand-written) + pygments.css (generated)
requirements.txt           Flask, Markdown, Pygments (installed into .venv/)
```

- **Chapters** live under `units/`, globbed by numeric filename prefix
  — `content_loader.py` orders them `01_`, `02_`, ... and the sidebar
  just iterates whatever `load_units()` returns.
- **Interview categories** live under `interview_questions/`, one file
  per topic, also ordered by numeric prefix.
- Both content types show up in the sidebar automatically. Adding a
  new chapter or exercise never requires touching a template.

## Running the app

```bash
source .venv/bin/activate
python3 app.py
```

Then open **http://127.0.0.1:5001**.

It runs on port 5001, not 5000 — on macOS, AirPlay Receiver / Control
Center squats on port 5000 by default, which would otherwise conflict.

Dependencies (Flask, Markdown, Pygments) are pinned in
`requirements.txt` and installed into `.venv/`.

## How to make changes

This app has exactly one rule: **edit the `.py` files, not the
templates.** The two content types use different comment formats, so
pick the right one.

### Adding/editing a chapter (general Python topics)

Edit one of the `units/NN_name.py` files, or add a new one with the
next numeric prefix (e.g. `units/09_something.py`).

```python
# Chapter N: Title

# --- Module Name ---
# Theory: one short sentence explaining the concept.
some_code = "here"
print(some_code)
```

- The file's first line (`# Chapter N: Title`) sets the unit title.
- Each `# --- Module Name ---` block starts a new module/section.
- Only the **first** comment line right after the header becomes the
  prose explanation (a leading `Theory:` is stripped). Everything
  after that — more comments, blank lines, real code — is kept
  verbatim as the code block. So multi-line explanations are possible,
  but only line 1 renders as prose; keep the key point there.

### Adding an interview question

Pick the right category file under `interview_questions/` and append a
new block:

```python
# --- Exercise Title ---
# Difficulty: Easy
# @problem
# The problem statement, verbatim from the prompt.
# @hint
# A conceptual nudge (name the technique) without giving away the answer.
# @solution

def solution_function(...):
    ...

# @explanation
# Walks through why the solution works, referencing the real names above.
```

- Sections are opened by exact marker lines: `# @problem`, `# @hint`,
  `# @solution`, `# @explanation`. Everything after a marker belongs
  to that section until the next one.
- **`@solution` is required**, even with nothing but a blank line
  before the function — code left directly under `@problem`/`@hint`
  with no `@solution` marker gets silently swallowed into the prose
  instead of becoming a code block. This is the most common mistake.
- `@hint` is optional.
- Write solutions in vanilla Python (basic loops, dicts/sets — no
  `collections.Counter`-style shortcuts) unless asked otherwise; this
  is a fundamentals cheat sheet.
- A category file can hold multiple exercises — just repeat the
  `# --- Title ---` block, in the order you want them to render.

**Always verify a new/edited exercise before calling it done:**
1. Run `load_categories()`, find the exercise, print every field —
   confirm `hint`/`problem`/`code`/`explanation` are non-empty and not
   bled into each other.
2. `exec()` the parsed `code` string and run it against a couple of
   concrete test cases.
3. Start the app, `curl` the category page, and check the new
   heading's `id`, difficulty badge, hint blockquote (if any), and the
   `<details class="solution-toggle">` block are present.
4. Confirm the sidebar/home page counts updated and spot-check one
   other route still returns 200.
5. Stop the dev server (`pkill -f "app.py"`) when done.

### Styling

- `static/style.css` is the single, hand-written stylesheet (red/white
  theme).
- `static/pygments.css` is **generated**, not hand-written. Regenerate
  it after changing the Pygments style:
  ```bash
  python3 -c "from pygments.formatters import HtmlFormatter; print(HtmlFormatter(style='friendly').get_style_defs('.codehilite'))" > static/pygments.css
  ```

### No JavaScript

The app is JS-free by design. The solution show/hide toggle is a
native HTML `<details>`/`<summary>` element styled with CSS attribute
selectors (`details[open]`), not a script. Keep it that way unless
explicitly asked to add JS.

## Current content

- 8 chapters: basics, control flow, functions, working with files,
  advanced function concepts, classes/OOP, third-party packages (pip),
  fetching data.
- 18 interview-question categories exist as files; most are currently
  empty placeholders (only "Arrays and Hashing" has exercises so far).
  An empty category is a valid state and renders an empty-state
  message — that's expected, not a bug.
